# 사용자 체크리스트 — 사람이 직접 만들거나 결정해야 할 것

> 에이전트가 대신할 수 없거나, 대신하면 제품 의도가 흐려지는 항목들입니다.
> 새 프로젝트를 시작할 때 이 목록을 복사해 체크하세요.

## P0 준비

- [ ] 스타터 템플릿 선택(기술 스택 고정 여부 판단)
- [ ] 사용할 코딩 에이전트와 구독 계정 준비
- [ ] 공통 스킬 선택(예: wiki, grill-me, 코드 스타일)
- [ ] 저장소 위치·원격 저장소 여부 결정

## P1 요구사항

- [ ] **요구사항 문서 직접 작성**: 한 줄 정의, 왜 만드는가, 사용자 흐름, 최종 결과물, 확장 계획
- [ ] 참고 서비스·레퍼런스 목록
- [ ] 절대 하지 않을 것(Non-goals) 명시 — 예: Vanilla Studio의 "생성형 AI 배제"

## P2 상세 기획

- [ ] 인터뷰 질문에 대한 결정(연동 방식, MVP 범위, 대상 OS, 정책 등)
- [ ] 에이전트가 제안한 `Proposed` 결정 검토 → Accepted/거절
- [ ] 기획서 승인
- [ ] 라이선스 리스크에 대한 판단(필요 시 법률 검토)
- [ ] 기획 보강: 에이전트가 놓친 제품 관점(예: 컬러 팔레트)과 따라야 할 업계 표준(예: DESIGN.md) 지정
- [ ] 참고 자료 링크 제공(예제 갤러리·에셋 카탈로그)과 용도 설명

## P3 구현 계획

- [ ] 마일스톤 우선순위와 일정 감각
- [ ] PoC 실패 시 대안 선택
- [ ] 품질 기준이 될 **골든 샘플 시나리오** 작성(예: 샘플 브리프 5종)
- [ ] 실제 에이전트·구독 사용량이 드는 PoC 범위 동의(예: "Claude Code만 먼저 검증", "사용량 동의")
- [ ] PoC로 드러난 정책 결정 확인(예: D-018 에이전트 세션 격리)
- [ ] 작업 중 추가한 개인 자료(레퍼런스 이미지 등)는 저장소에 넣을지 결정(Vanilla: `Docs/images/`는 로컬 전용)
- [ ] 원격 저장소 생성·연결, 병합·push 승인

## P4 구현

- [ ] 마일스톤 데모 확인 및 방향 피드백
- [ ] 브랜딩 자산(앱 이름, 로고, 아이콘, 색) — `BRANDING.md` 절차
- [ ] UI 문구 톤(ko/en)

## P5 검증

- [ ] 실제 사용해 보기, 버그·불편 보고
- [ ] 릴리스 가능 판단

## P6 릴리스

- [ ] 버전 번호, 릴리스 노트 검토
- [ ] 코드 서명 인증서, 배포 채널(GitHub Releases 등)
- [ ] **push·배포 실행 승인**

## P7 회고

- [ ] 단계별 회고에 사람 관점의 교훈 추가
- [ ] 강의에서 보여줄 장면·자료 선정
